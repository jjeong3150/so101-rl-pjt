## 과제와 정책

출발점은 `(0.23, -0.085)`m, 플레이트 중심은 `(0.23, 0.10)`m입니다.
공 지름은 4.4cm, 질량은 25g입니다. 시작 위치의 가로·세로에 각각 최대 1.5cm의 변화를 줍니다.
출발 패드와 도착 플레이트에는 벽이나 칸막이가 없습니다.
초기 손목 회전(`wrist_roll`)은 이전 자세에서 180도 반전해 카메라 거치대가 위쪽에 오도록 설정합니다.
이 초기값은 학습·CPU 평가·뷰어에 공통 적용하며, 에피소드가 시작한 뒤에는 정책이 손목 각도를 선택합니다.

정책은 팔 다섯 관절과 집게의 목표 각도 변화량 6개를 직접 선택합니다.
MuJoCo 위치 액추에이터가 목표를 실행합니다. 미리 작성한 집기 경로나 IK 제어기는 없습니다.
관측은 카메라 RGB 영상과 관절 관련 수치 25개입니다. 아래 입력을 합쳐 PPO로 학습합니다.

| 정책·가치망 입력 | 내용 |
|---|---|
| 손목 카메라 | 원본 모델의 `wrist_cam`, 64×64 RGB |
| 작업대 고정 카메라 | 추가한 `overview_cam`, 64×64 RGB |
| 영상 이력 | 카메라마다 최근 2프레임, 총 12채널. 오래된 프레임의 손목·외부 RGB 다음 최신 프레임 순서 |
| 관절 관련 수치 | 관절 각도6·속도6·목표 각도6·이전 명령6·남은 시간1 |

작은 CNN(16/32/32채널 → 128 특징)이 영상 특징을 만들고, 관절 수치와 합쳐 행동과 가치를 예측합니다.
CNN도 PPO와 함께 처음부터 학습합니다. Actor와 Critic 모두 같은 영상·관절 입력을 사용합니다.
**공/플레이트의 정확한 좌표, 공 속도, 손끝의 월드 좌표, 접촉·집기·성공 이력은 두 망의 입력에 넣지 않습니다.**
시뮬레이터의 정확한 상태는 물리·보상·성공 판정과 사람에게 보여주는 지표에만 사용합니다.
영상 입력 추가만으로 정책이 공을 인식하거나 집기에 성공했다고 주장하지 않습니다.

영상은 4제어 스텝마다 약 12.5Hz로 갱신하고, 제어는 50Hz입니다.
프레임은 `uint8`로 보관하고 CNN에 넣을 때만 정규화해 메모리 사용을 줄입니다.
초기화 시 새 에피소드의 영상으로 이력을 채우고, 종료 상태와 초기화 상태의 영상이 섞이지 않도록 처리합니다.
모든 카메라는 가상 시뮬레이션 카메라입니다. 실제 USB 카메라나 학생의 웹캠을 사용하지 않습니다.

실제로 양쪽 집게로 잡아 들어 올린 이력이 있고, 공 전체가 플레이트 안쪽에 놓여야 성공합니다.
바닥에서 공을 밀어 옮기는 것만으로는 성공하지 않습니다.

## 보상

| 항목 | 보상 |
|---|---:|
| 접근·집기·들기·운반·놓고 물러나기 진척 | `3 × (0.995 × Φ다음 − Φ이전)` |
| 최초 실제 들어 올림 | 에피소드당 한 번 +3 |
| 최종 성공 | +50, 에피소드 종료 |
| 비정상 상태·작업 공간 이탈 | −10, 에피소드 종료 |
| 시간 경과 | 매 제어 스텝 −0.002 |
| 큰 명령 | `−0.001 × mean(a²)` |
| 급격한 명령 변화 | `−0.002 × mean((a−이전a)²)` |

`a`는 tanh를 거친 여섯 명령이며 실제 에너지나 가속도를 측정한 감점은 아닙니다.
`Φ`는 아래 점수의 합입니다. 점수 전체를 매번 보상으로 주지는 않습니다.

| 진척 점수 | 계산 |
|---|---|
| 공 접근 | `0.5 × (1 − tanh(10 × 손끝–공 거리))` |
| 현재 양쪽 집게 접촉 | `0.5 × 양쪽 접촉 여부` |
| 잡은 채 들어 올림 | `0.75 × clip(초기 대비 높이 / 6cm, 0, 1) × 양쪽 접촉 여부` |
| 들어 올린 공을 목표로 운반 | `1.5 × 들어 올림 이력 × exp(−10 × 목표 거리)` |
| 플레이트에 놓고 물러나기 | 최대 3. 놓기 이력·실제 플레이트 지지·안쪽 위치·집게 비접촉을 요구하고 높이 오차와 후퇴 거리를 반영 |

놓고 물러나는 상태에 충분한 점수를 주도록 설계했습니다. 반복 칸 유지 보상과 중복 완료 보상은 제거했습니다.
실제 종료(성공·물리 실패)의 다음 `Φ`는 0입니다. 시간 제한은 critic 값으로 이어 평가하므로 다음 `Φ`를 유지합니다.
PPO와 진척 보상은 할인율 0.995를 공유합니다.
[Potential-based reward shaping 논문](https://people.eecs.berkeley.edu/~pabbeel/cs287-fa09/readings/NgHaradaRussell-shaping-ICML1999.pdf)을 참고했습니다.
별도 보너스와 명령 감점도 있어 원래 목표와 최적 정책이 같다는 보장은 주장하지 않습니다.

## 판정

- **들어 올림:** 양쪽 집게에 각각 0.05N 초과의 실제 힘 접촉, 손끝–공 거리 5.5cm 미만, 초기보다 공 중심이 4cm 높아진 상태를 5스텝(0.1초) 유지합니다.
- **놓기 이력:** 들어 올린 뒤 집게를 열고 공에서 떨어졌는지 기록합니다. 이것만으로 성공은 아닙니다.
- **최종 성공:** 공 전체가 플레이트 가장자리에서 5mm 이상 안쪽에 있고, 높이 오차 4mm 이내·속도 3cm/s 미만이어야 합니다. 실제 공–플레이트 지지 접촉, 집게 비접촉, 손끝–공 거리 6cm 초과를 25스텝(0.5초) 유지합니다.

성공 위치는 중심의 작은 점이 아닌 플레이트 내부 영역입니다. 진척 점수는 중앙으로 운반하는 것을 선호합니다.
판정은 행동 순서를 실행하는 제어기가 아닙니다. 모든 보상은 처음부터 적용하며 커리큘럼·시연 데이터·계층형 정책은 포함하지 않습니다.

## 병렬 학습과 뷰어

영상 과제 기본값은 **T4 환경 4개 / L4 환경 8개, rollout 64스텝, minibatch 128**입니다.
해상도·영상 갱신 횟수·작은 CNN으로 계산량을 줄이는 설정이며 실제 메모리와 속도는 측정하지 않았습니다.
메모리가 부족하면 노트북에서 환경 수를 2개로 줄일 수 있습니다.
에피소드 최대 1,000 제어 스텝(시뮬레이션 20초), 제어 스텝당 물리 계산 20회입니다.
CUDA 그래프 캡처는 끄고 GPU의 일반 MJWarp step 경로를 사용합니다.

GPU 환경들이 하나의 영상 정책을 병렬 학습합니다. 뷰어의 물리는 별도 CPU MuJoCo 환경 한 대에서 계산합니다.
뷰어·평가 카메라도 GPU의 같은 MJWarp 렌더러를 사용합니다. CPU 물리 평가가 GPU 자원을 전혀 쓰지 않는다는 뜻은 아닙니다.
렌더링은 `mujoco-warp==3.16.0`의 `create_render_context → refit_bvh → render → get_rgb` 경로이며 OpenGL/EGL을 사용하지 않습니다.
[버전 고정 공식 렌더링 튜토리얼](https://github.com/google-deepmind/mujoco_warp/blob/v3.16.0/notebooks/tutorial.ipynb)을 참고했습니다.
뷰어의 **정책이 보는 영상** 패널은 해당 정책에 전달한 최신 RGB 프레임을 그대로 표시합니다.
3D 화면의 목표 사각형·성공 표시 오버레이는 정책의 카메라 영상에 넣지 않습니다.
학습 시작 시 정책·최신 정책·무작위 행동을 비교하며, 정책은 에피소드 시작 때 반영합니다.
뷰어 제어 스텝과 학습 업데이트는 다른 값입니다. 보상뿐 아니라 들어 올림·놓기 이력 비율과 최종 성공률을 함께 확인하세요.
별도 탭은 본인 Colab 세션의 프록시 주소를 사용합니다. 연결되지 않으면 내부 화면을 사용하고 런타임은 열어 두세요.
